# Code Review Guide: Builder Bundle (bb)

> **Last updated**: 2026-08-19
> **Generated by**: /bb:review-setup
> **Stack**: a Claude Code plugin published through a one plugin marketplace. Markdown is the
> product (skills, references, agents), Python (stdlib only) does the deterministic work, one
> TypeScript script validates frontmatter, and Bun plus lefthook plus GitHub Actions run the
> checks. There is no test suite: see "Repo patterns".

## Purpose

Code review rules for **Builder Bundle (bb)**: the pre-PR reference for whoever opens a
change, and the rule source for `/bb:review`, which reads this file fresh on every run. Every
rule here was accepted by the maintainer, and carries the repo path that shows it.

Two files this guide defers to, because they own their subject: `.claude/CLAUDE.md` for the
repo's structure and conventions, and `plugins/bb/references/doc-style.md` for every sentence
the plugin writes. A rule below that restates one of them cites it as evidence.

## Severities

| Level      | Meaning                                                              | Review impact                                 |
| ---------- | -------------------------------------------------------------------- | --------------------------------------------- |
| **HIGH**   | Non-negotiable: broken contract, silent failure, a check CI fails on | Verdict: CHANGES REQUESTED                    |
| **MEDIUM** | Needs judgment; 3+ in one PR signals decay                           | 1–2: NEEDS DISCUSSION / 3+: CHANGES REQUESTED |
| **LOW**    | Informational, a nit                                                 | Never affects the verdict                     |

Five rules are enforced by a program instead of by a reader: BB001, BB002, BB022, BB024 and
BB027. They fail the branch instead of collecting a comment, so they sit at HIGH.

## Pre-PR checklist

1. `bun install`, then `bun run validate` for the frontmatter of every `SKILL.md` and every
   `agents/*.md` (BB001, BB002).
2. `python3 plugins/bb/skills/spec/scripts/lint_spec.py .bb/<slug>/spec.md` for any spec the
   change touches (BB022).
3. `bun run fmt` before committing. `lefthook.yml` already runs it on staged `*.{json,md}` and
   stages the fix, and CI runs `bun run fmt:check` (BB027).
4. Read the diff's prose against the rules a program cannot see: no dash, sentence case in a
   heading, one name per thing, a table cell short enough to read across (BB008, BB010, BB012,
   BB013).
5. Removed a field, a page or a file? Grep for its readers in the same commit (BB030).
6. Visible to whoever installs the plugin? Bump `version` in
   `plugins/bb/.claude-plugin/plugin.json` and add the `CHANGELOG.md` entry (BB028).
7. Changed the skill count? Fix the counts in `README.md` and in the plugin's `description`
   (BB029).

CI runs steps 1 to 3 on every pull request touching `plugins/**`, `.bb/**`, `**/SKILL.md`,
`**/agents/**` or the workflow itself, so opening the pull request is a valid way to run them.

#### BB001: Frontmatter carries `name` and `description`

- **Category**: contracts
- **Severity**: HIGH
- **Description**: every `SKILL.md` and every `.md` directly under an `agents/` directory opens
  with a YAML frontmatter block carrying a string `name` and a string `description`. Without
  them the harness has nothing to register the skill under and nothing to decide when to invoke
  it.
- **Evidence**: `validateFrontmatter` in `.github/scripts/validate-frontmatter.ts`, the
  `Validate frontmatter` step of `.github/workflows/validate.yml`, and the `validate` hook of
  `lefthook.yml`.
- **Do**:
  ```yaml
  ---
  name: profile
  description: Calibrate once who is on the other side, and every bb session after this one is calibrated.
  ---
  ```

#### BB002: An agent is read-only by its `tools:` list

- **Category**: security
- **Severity**: HIGH
- **Description**: an agent definition carries `tools:`, and that list never names `Write`,
  `Edit`, `MultiEdit`, `NotebookEdit` or `*`. Omitting the field inherits every tool, which is
  the same defect written shorter. With `Bash` on the list the surface is narrowed and not
  closed, so the list is a scoping decision, not a guarantee to advertise.
- **Evidence**: `FORBIDDEN_AGENT_TOOLS` and `validateAgentTools` in
  `.github/scripts/validate-frontmatter.ts`; `plugins/bb/agents/bb-review-finder.md` and
  `plugins/bb/agents/bb-review-verifier.md`.
- **Do**:
  ```yaml
  tools: Read, Grep, Glob, Bash
  ```

#### BB003: The skill folder is named after its `name`

- **Category**: contracts
- **Severity**: HIGH
- **Description**: a skill lives at `plugins/bb/skills/<name>/SKILL.md`, and `<name>` is
  identical to the frontmatter `name`, because that name is what `/bb:<name>` resolves. Names
  are verb led where the skill does something, and carry no trilha prefix: the trilha grouping
  is a `README.md` concept.
- **Evidence**: the naming conventions of `.claude/CLAUDE.md`; every folder in
  `plugins/bb/skills/`.

#### BB004: A phased `SKILL.md` is a router

- **Category**: quality
- **Severity**: HIGH
- **Description**: a skill with phases or modes keeps `SKILL.md` lean: what the skill is, how it
  decides which phase applies, and one line per phase pointing at its reference. The per-phase
  material lives in the skill's `references/` and is loaded only when that phase runs.
  `.claude/CLAUDE.md` calls a monolithic `SKILL.md` that inlines every phase a defect, not a
  style choice.
- **Evidence**: "Progressive disclosure (mandatory for fused skills)" in `.claude/CLAUDE.md`;
  `plugins/bb/skills/review/SKILL.md` routing to seven `references/front-*.md`.

#### BB008: No dash in the prose

- **Category**: quality
- **Severity**: HIGH
- **Description**: where a dash would go, write a comma, a colon, a period, or rewrite the
  sentence. Two things keep the character: a functional token (inside a command, a regex, a path
  or a value a format reserves) and a verbatim quote, which keeps its source's punctuation. A
  number range keeps its en dash. Inside frontmatter the colon is unavailable too, because `: `
  in an unquoted value reads as a nested mapping and fails the parse.
- **Evidence**: the Dashes section of `plugins/bb/references/doc-style.md`.
- **Do**:
  ```markdown
  The gate writes nothing of its own: the brief carries the journey.
  ```

#### BB009: Positive guidance, no anti-pattern catalog

- **Category**: quality
- **Severity**: HIGH
- **Description**: guidance is stated as what to do. A catalog of anti-patterns writes the
  unwanted behavior into the prompt, which primes it; one sharp caution is allowed where
  negation is the clearest signal. An irreversible hazard is enforced by capability scoping
  instead, the way BB002 enforces read-only agents.
- **Evidence**: the writing guidelines of `.claude/CLAUDE.md`.

#### BB015: Python, stdlib only

- **Category**: contracts
- **Severity**: HIGH
- **Description**: a script in this repo imports from the standard library and nothing else.
  Scripts run on whatever machine has the plugin installed, so a third-party import is a
  dependency the caller never agreed to install.
- **Evidence**: the Scripts section of `.claude/CLAUDE.md`; the imports of
  `plugins/bb/hooks/inject_operating_context.py` and
  `plugins/bb/skills/spec/scripts/lint_spec.py`.
- **Do**:
  ```python
  import json
  import os
  ```

#### BB016: Deterministic work goes in a script

- **Category**: quality
- **Severity**: HIGH
- **Description**: parsing, formatting, data transformation, file manipulation and JSON
  processing belong in a Python script the workflow calls. Model reasoning is reserved for
  judgment, synthesis and creative decisions. A deterministic step written as prose is a step
  that produces a different result on every run.
- **Evidence**: the scripting principle of `.claude/CLAUDE.md`;
  `plugins/bb/skills/review/scripts/group_candidates.py` and
  `plugins/bb/scripts/gather_context.py`.

#### BB017: A session hook never blocks the session

- **Category**: correctness
- **Severity**: HIGH
- **Description**: a hook runs on every session in every repo where the plugin is enabled, so
  its failure mode has to be silence and exit 0. Input that is missing, unreadable or malformed
  reads as absent, never as an error the person has to fix first.
- **Evidence**: the module docstring and `read_config` in
  `plugins/bb/hooks/inject_operating_context.py`.
- **Do**:
  ```python
  try:
      with open(CONFIG_PATH, encoding="utf-8") as f:
          config = json.load(f)
  except (OSError, ValueError):
      return {}
  ```

#### BB022: A spec carries its frontmatter and its sections

- **Category**: contracts
- **Severity**: HIGH
- **Description**: `.bb/<slug>/spec.md` opens with a frontmatter block carrying `status` (a valid
  value), `created` as `YYYY-MM-DD` and `slug`, and carries the fixed sections the other skills
  read. The lint answers `E001` for the block, `E002` for a missing section, `E003` for a dead
  section name and `W003` naming the current one.
- **Evidence**: `plugins/bb/skills/spec/scripts/lint_spec.py`, the `Lint specs` step of
  `.github/workflows/validate.yml`, and the contract in `plugins/bb/references/spec-state.md`.
- **Do**:
  ```yaml
  ---
  status: done
  created: 2026-08-19
  slug: bb-config
  ---
  ```

#### BB023: A spec describes what to build now

- **Category**: quality
- **Severity**: HIGH
- **Description**: a spec in `.bb/` says what to build as it stands. How it got there, what a
  closer read corrected, which alternative lost, goes in the commit body. Recounting the
  conversation inside the document is what makes specs unreadable.
- **Evidence**: the describes-versus-recounts rule of
  `plugins/bb/skills/spec/references/spec-format.md`; the Commits section of
  `.claude/CLAUDE.md`.

#### BB024: No AI attribution

- **Category**: contracts
- **Severity**: HIGH
- **Description**: no commit message, pull request body or code comment carries a co-author
  trailer, a generated-by line or any other AI attribution.
- **Evidence**: the Commits section of `.claude/CLAUDE.md`; `git log` across the repo.

#### BB025: Conventional commit subject

- **Category**: contracts
- **Severity**: HIGH
- **Description**: `<type>(<scope>): <description>`, where the scope is the skill name (`spec`,
  `brisar`, `review`), `hooks` for the hook layer, or `repo` for a repo wide change. The subject
  may stay in Portuguese; see BB031.
- **Evidence**: the Commits section of `.claude/CLAUDE.md`; `git log --oneline`.
- **Do**:
  ```text
  refactor(brisar): drop the state file, the brief carries the journey
  ```

#### BB026: The commit body carries the rationale

- **Category**: quality
- **Severity**: HIGH
- **Description**: the body says why the decision changed, what a closer read of the source
  corrected, and which alternative lost and on what grounds. It is the half of the change that
  the file itself must not carry (BB023).
- **Evidence**: the Commits section of `.claude/CLAUDE.md`; the body of `e06fcc5`.

#### BB027: `oxfmt --check .` is clean

- **Category**: contracts
- **Severity**: HIGH
- **Description**: markdown and JSON are formatted by `oxfmt` at the version `package.json`
  pins. Table alignment is the usual cause of a red run, because editing one cell shifts a whole
  column. `bun run fmt` writes the fix, and `lefthook.yml` runs it on staged files.
- **Evidence**: `package.json` (`fmt`, `fmt:check`, `oxfmt` pinned at 0.43.0), the
  `Check formatting` step of `.github/workflows/validate.yml`, `lefthook.yml`.
- **Do**:
  ```bash
  bun run fmt
  ```

#### BB030: Removing a field removes its readers

- **Category**: correctness
- **Severity**: HIGH
- **Description**: when a commit removes a field, a page or a file, it removes every pointer at
  it in the same commit. A pointer left behind is worse than a broken link, because the model
  obeys it: an instruction to update `current_phase` writes a field nothing reads, and a
  condition on a field nobody writes any more is a branch that never fires.
- **Evidence**: `7a35250` removed `.brisar/session.yaml` and left six live pointers
  (`current_phase`, `gate.design_brief`, `design_path`, and a deleted page still cited by its
  readers), which `e06fcc5` closed.
- **Do**:
  ```bash
  grep -rn "current_phase\|gate\.design_brief\|design_path" plugins/
  ```

#### BB032: Python is invoked as `python3`

- **Category**: correctness
- **Severity**: HIGH
- **Description**: every command a skill, a hook or a workflow prints or runs calls `python3`. On
  a machine where only `python3` is on the PATH, a hook command that says `python` fails at
  session start, and because a hook must not block (BB017) it fails in silence: the frame simply
  never arrives.
- **Evidence**: `.github/workflows/validate.yml` and the skills call `python3 …/lint_spec.py`;
  `plugins/bb/hooks/hooks.json` calls `python`, which is the one deviation in the repo today.
- **Do**:
  ```json
  { "command": "python3 \"${CLAUDE_PLUGIN_ROOT}/hooks/inject_operating_context.py\"" }
  ```

## Repo patterns

### There is no test suite

Nothing in this repo runs a unit test, and a review should not ask for one. The checks are the
frontmatter validator, the spec lint and the formatter, all three in
`.github/workflows/validate.yml` and two of them again in `lefthook.yml`. What replaces a test
here is the contract page a change has to stay consistent with: `doc-style.md` for prose,
`spec-state.md` for the `.bb/` folder, `handoff-gate.md` for a gate.

### The product is prose the model obeys

Most files are instructions a model reads at runtime, so a stale sentence behaves like dead code
that still executes. That is why BB030 sits at HIGH and why the prose rules are not cosmetic: a
heading, a field name and a path are the interface.

### Commits

Conventional subject scoped by skill (BB025), rationale in the body (BB026), no AI attribution
(BB024). Subjects run in Portuguese or English (BB031); the files are English.

### Security surface

Two guards, both mechanical. Agents are read-only through `tools:`, checked by CI (BB002).
Scripts import only the standard library (BB015), so nothing arrives from a registry at run
time. `__pycache__/` is ignored by `.gitignore`.

### Error handling

The hook layer's rule is silence over failure (BB017). The spec lint takes the opposite stance:
it names a code (`E001` to `E005`, `W001` to `W004`) and exits non-zero, because it runs in CI
where a red run is the point.
