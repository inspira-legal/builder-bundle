# Implement

Build the validated brief in the working tree — taking it from alignment to code that's ready to ship. The trio's executor: it builds the backlog, then offers to ship.

## Prerequisites

A validated brief with a `## tasks` checklist, resolved per the task-state contract (plugin-level `references/task-state.md`): `.bb/tasks/<slug>/spec.md`. If there's no brief for this work, stop and suggest `/bb:spec` first — implementing without alignment is exactly what the spec prevents.

## Workflow

1. **Load the brief.** Read it whole — the opening and the sections above the spine describe the thing and how it's put together, and they're written to be read once, start to finish. Then the spine: the `## decisions` (including the **reuse** notes), the `## behavior` map (happy path + edge→outcome — **build to this; it's the acceptance contract**), what's **out of scope** (a hard line — do not build it), and the `## tasks` slices.
2. **Reuse first.** Before writing anything, confirm the code/patterns named in the brief's reuse notes still exist, and prefer extending them over reinventing. If one has moved or changed, flag it and adjust rather than guessing — the path you found outranks the one the brief names. If one is **gone**, that's step 7's valve firing, not something to work around.
3. **Pick the build mode, then implement every unchecked slice, respecting `dep:`.** The mode first — one agent per slice dispatched as a dynamic workflow, or the slices built in this context — per the plugin-level `references/build-mode.md`. A `/bb:delegate` run arrives with the answer already picked, so it isn't asked twice. With no `Workflow` tool in the session — the setting is off, or the client predates it — there's nothing to offer: build in context and say so in one line, so the downgrade doesn't read as a preference. **In workflow mode:** author the script per the plugin-level `references/build-slices-workflow.md`, run its pre-invoke checklist, invoke `Workflow`, and read the result — the slices it built are already committed and ticked, `pendingVerifica` names the ones whose proof is CI, and a non-null `stopped` is step 7 firing from inside the run. Everything below in this step, and steps 4–6, is the in-context path. A slice reads `— <entrega> → behaviors N · dep: <slices> · verifica: <como>`: `dep:` says what has to land first (`—` means nothing does), and the behaviors it cites are what it has to satisfy. Follow that order, not the list order. Each slice is a thin end-to-end cut — build it as one. Stay inside scope; the out-of-scope bucket is a boundary, not a suggestion. When a slice forces a **stack choice** the brief didn't close (framework, package manager, tooling), consult the manifesto first (plugin-level `references/consult-manifesto.md`).
4. **Keep the gate green as you go.** Detect the project's checks in this order of authority: CLAUDE.md / docs → CI workflow files → `package.json` / `justfile` / `Makefile` / `pyproject.toml`. Run lint/format/typecheck/tests; fix before moving on. Run what CI runs, not a subset.
5. **Run the slice's `verifica:` before you tick it.** It names how that slice is proven — a test, a command, reading the result, green CI. It's the slice's own check, on top of the project gate; a slice whose `verifica:` didn't run is a slice that isn't done.
6. **Commit per slice, check the box.** Commit in logical units (conventional style; no AI attribution), and tick that slice's `- [ ]` → `- [x]` in the `## tasks` section as it lands — so progress is visible and a partial run is resumable.
7. **Safety valve.** If a slice reveals the idea was underspecified — surprises pile up, scope wants to grow, a decision the brief skipped now bites — STOP and hand back to `/bb:spec` to re-spec it. Don't improvise past the brief; that's the signal alignment was incomplete. A reuse note pointing at code that's **gone** fires the same valve — the brief was written against something that no longer exists, so it's the brief that has to change. In workflow mode both arrive as a returned blocker instead of a realization mid-build. Two stage-zero blockers are **not** the brief's fault and route elsewhere: a gate the run has no permission to execute (report the command so the allowlist can be widened) and a tree already red before slice 1 (the broken gate predates the build; report it so the red gets fixed where it lives). All three stop the build, and the tree is left as the run left it, for diagnosis.
8. **Hand off — offer to ship, or chain.** Summarize what landed against the task list (done / skipped / blocked). Then branch on how the run went:
   - **Clean** (every slice landed, gate green): offer ship via a handoff gate (plugin-level `references/handoff-gate.md`) — lead **"Shipar agora"** (invoke `/bb:ship`) against **"Encerrar aqui"** (print the command and stop). Either path, ship loads this same brief as the intent. (When the whole run is wanted up front without this stop, that's `/bb:delegate` — it drives this build loop and chains into ship itself; implement, whether picked at the spec gate or run by command, is the build-then-decide path.)
   - **Not clean** (a slice blocked, or the safety valve fired): report done/skipped/blocked and hand back where step 7 sends it — `/bb:spec` when the brief is what has to change, the allowlist or the pre-existing red gate when it isn't. Either way **don't** offer ship: a partial build shouldn't become a PR that claims to satisfy the brief.
