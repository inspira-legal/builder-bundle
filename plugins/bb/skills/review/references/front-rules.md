# Front: rules — deviations from the project's own written rules

The other fronts judge the diff against general engineering criteria. This one
judges it against **what this project wrote down**, and it reports each deviation
with the rule quoted next to the line that breaks it. That citation is the whole
point: a rule finding a maintainer can't verify in two seconds is worth less than
no finding.

## 1. Collect the rule sources

In precedence order (a later source never overrides an earlier one, it adds):

1. **`CODE_REVIEW_GUIDE.md`** at the repo root — read fresh every run, never
   cached. Generated by `/bb:review-setup`; carries rule IDs, severities
   (HIGH/MEDIUM/LOW), evidence paths, and Do/Don't examples. This is the
   authoritative source when it exists.
2. **The CLAUDE.md set that governs the changed files** — the user-level
   `~/.claude/CLAUDE.md`, the repo-root `CLAUDE.md`, plus any `CLAUDE.md` or
   `CLAUDE.local.md` sitting in a directory that is an **ancestor of a changed
   file**. A directory's CLAUDE.md applies only to files at or below it: don't
   apply a sibling package's rules to this diff.
3. **In-code guidance** — comments in or immediately around the changed code that
   state a constraint ("keep this in sync with X", "callers must hold the lock").
   A change that contradicts one is a deviation.

Report the sources you actually read at the top of the front's section, so the
user knows what the front was judging against. No guide and no applicable
CLAUDE.md → the front had nothing to check; say that in one line.

## 2. The citation discipline

Flag a deviation only when you can produce **both** halves:

- the **exact rule text**, quoted, with its ID (guide) or source path + section
  (CLAUDE.md / comment), and
- the **exact line** in the diff that breaks it, quoted.

Everything that fails that test stays out: style preferences, "spirit of the
document" inferences, rules you're paraphrasing from memory, a rule whose scope
doesn't reach the changed file. When a rule _nearly_ applies, it isn't a finding.

Two more filters, both about not manufacturing work:

- **CLAUDE.md is written for the agent authoring code**, and not every instruction
  in it is a review rule (setup notes, tone, tooling preferences). Apply the ones
  that describe the code; skip the ones that describe the session.
- **A deviation the code explicitly silences** — a lint-ignore with a reason, a
  comment justifying the exception — is the project exercising its own escape
  hatch. Leave it.

## 3. Finding shape

```
# | regra (ID ou path§seção) | "texto da regra" | file:line | linha que desvia | severidade | fix
```

Severity comes from the guide's ladder when the rule is a guide rule. A CLAUDE.md
or in-code deviation ranks **MEDIUM** unless its own text states the stakes
(mandatory/never/quebra) — then HIGH.

Cap: 8 candidates. When the diff breaks the same rule in many places, report it
once with the rule cited and the locations listed, not once per location.

## 4. Verdict impact and drift

- When the guide defines a verdict rule, it decides: e.g. "qualquer HIGH ⇒ CHANGES
  REQUESTED", "3+ MEDIUM ⇒ CHANGES REQUESTED". Carry it into the report so the
  user sees where the diff lands.
- **Guide drift** is its own finding, reported separately from the deviations: a
  rule citing a path, pattern, or command that no longer exists in the repo. One
  line each, plus the pointer — regenerate with `/bb:review-setup`, which does a
  delta update instead of rewriting the guide.
- A convention the diff clearly should have followed that **no source states** is
  not a deviation. It's a candidate rule: mention it once at the end of the
  section as something `/bb:review-setup` could capture.
